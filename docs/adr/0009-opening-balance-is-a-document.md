# 期初是启用日前的一类单据，导入是它的另一个录入口

**状态**：已采纳（2026-11-24，「期初与数据导入」）

系统上线时，库存、往来、资金三本账都只有一个起点：启用日前一日。这个起点不是主数据上的几个余额字段，而是三本账各自的流水；每一组流水都长在一张**期初单**上——`doc_type = opening`，用 `opening_kind` 分库存 / 往来 / 资金三类，沿用单据骨架（草稿 → 生效 → 版本链 → 红冲 → 作废）。期初往来一个往来对象一张单，每行带原发生日期，账龄因此成立；期初库存按「数量 × 成本单价」入账，单价默认取参考进价。启用日不是参数，而是从最早一张生效期初单推出来的。期初改错与别的单据一样走改单（红冲 + 重开），不设日历冻结、不加审核。Excel 导入是这些单据的另一个录入口：五张模板，主数据逐行 upsert，期初整批生成单据，每个批次可整批撤销。

## 考虑过的方案

- **三张期初录入口（六家一致）**：星辰 / 精斗云 / T+ / 好生意 / 管家婆 / 秦丝都把三本期初放在「初始化」下的三个录入区。代价是它必须自带一套期初专属的更正动作（批量删除、清除、反结账、系统重建），那就是第二套更正机制；期初流水也没有单据可追。
- **期初记在档案字段上（精斗云、秦丝、好生意往来单位）**：客户档案上一个「期初应收款」加一个余额日期，最省事。代价是余额成了第二份真相，而且只有一个总数——T+ 从反面印证：按余额汇总结转之后「无法再按明细进行账龄分析」。
- **一张期初单装三类行**：三本账的事实来源（盘点表 / 欠条清单 / 银行余额）、时间语义、完成时点都不同，绑成一张会互相阻塞，上线最怕被最慢的那本账卡住。
- **启用日做成系统参数**：参数要人记得维护，而且会与期初单日期形成两处口径；派生值不会自相矛盾。
- **启用后锁死期初（六家一致）**：星辰「被核销过不支持修改」、T+「已被后续核销 / 已汇兑调整 / 已期末处理不允许改」——那是它们没有版本链的后果，不是产品偏好。照做就得把盘点单与日常收支单的界面提进 v1，再造一个「期初专属更正」入口。
- **期初导入部分成功（六家一致）**：好生意手册自己写着「重复导入会追加数据，系统不会覆盖，不会查重」，重复导入翻倍是它们的第一大翻车点；半个期初也是不可解释的账。
- **导入直接写流水、用批次号做幂等键**（「库存账本与移动加权平均」早先的建议）：批次数不进流水键，否则同一笔账有两种身份；流水必须追到单据。

## 后果

- 三类期初单共用单据骨架；期初单的改单与作废只对管理员开放。
- 每商品 / 每往来对象 / 每资金账户至多一条未红冲的期初流水；多张期初单可以并存（分批导入、后加账户、后加商品），但不得重复覆盖同一个对象。
- 期初往来行的 `party_entry.biz_date` 取行上的原发生日期，不取单据日期——这是全系统唯一一处「流水日期 ≠ 单据业务日期」，其余单据不变。
- 启用日 = 最早一张生效期初单的业务日期 + 1；任何期初单的业务日期不得晚于当前最早生效业务单据的业务日期 − 1；早于启用日的业务单据只能存草稿。
- 改期初 = 红冲该期初单全部流水 + 按新内容重开；库存走成本链重放，历史毛利可能被改写，报表标「最近重放时间」（ADR 0001 已要求）。这一点与六家都相反，代价是二次确认与历史数字会动。
- 导入两条通道：主数据逐行 upsert、部分成功；期初整批，先干跑零写入再执行。批次记录留文件哈希、行数与成败；期初批次可整批撤销（红冲）。
- 历史单据不进系统：系统只装启用日之后的生意，加上三本期初；旧单据留在旧系统或导成 PDF 归档。
